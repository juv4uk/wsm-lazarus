# Повторюваний D24 native-loop benchmark

## Розширена матриця компіляторів

До початкових SENS/C/Rust/Free Pascal додані чотири AOT-збірки для одного й того самого циклу: C++/Clang 18, Zig 0.17.0, Fortran/GFortran 13 і Swift 6.4.1. Їхні вихідні файли, параметри оптимізації та перевірені контрольні суми архівів описані в [toolchains.json](toolchains.json). `build.sh` збирає всі вісім виконуваних файлів, а `check-aot.sh` окремо перевіряє спільний результат і відхилення запуску без аргументу.

**Нижче наведені два окремі прогони розширеної матриці.** Кожен має 30 випадково переставлених блоків, по 50 запусків кожного виконуваного файла на зразок і окремі сирі дані. Усі вісім програм перевірені на однаковий код завершення `173`.

| Виконуваний файл | Версія та прапорці | Час / 50 запусків, прогін 1 / 2 | Package RAPL, Дж / 50 запусків, прогін 1 / 2 |
|---|---|---:|---:|
| SENS native ELF | вузький `BuildD12SumLoopELF` | 0,262 / 0,278 с | 6,21 / 6,90 |
| C / GCC | 13.3 `-O2` | 0,368 / 0,374 с | 9,50 / 9,56 |
| Rust | 1.99 `opt-level=2` | 0,153 / 0,162 с | 3,84 / 3,90 |
| Free Pascal | 3.2.2 `-O2` | 0,286 / 0,281 с | 7,47 / 6,84 |
| C++ / Clang | 18.1.3 `-O2` | 0,184 / 0,190 с | 4,59 / 4,76 |
| Zig | 0.17.0 `ReleaseFast` | 0,135 / 0,135 с | 3,33 / 3,23 |
| Fortran / GFortran | 13.3 `-O2` | 0,451 / 0,464 с | 10,36 / 12,33 |
| Swift | 6.4.1 `-O` | 0,496 / 0,525 с | 12,13 / 14,06 |
| Idle: `/usr/bin/true` | той самий хост і 50 запусків | 0,139 / 0,145 с | 3,42 / 3,42 |

Обидва прогони зроблені на Intel Core i5-6400, з прив’язкою до CPU 2, governor `powersave` і turbo увімкненим. У цьому конкретному cold-process вимірі Zig мав найменший batch time, а Rust — наступний. Різниця вимірює весь виконуваний файл разом із запуском процесу, ELF loader та парсингом аргументу, не ізольований час циклу. Idle-контроль майже такий самий за часом, як Zig; це означає, що запуск процесу вже займає більшу частину виміру.

Package RAPL — споживання всього процесорного пакета, а не окремої програми. У парній idle-діагностиці p10–p90 кожної мови перетинає нуль в обох прогонах, тож ці дані не встановлюють, яка мова спожила менше енергії. Не можна трактувати абсолютні joules таблиці як енергію виконання програми.

## Посилений RAPL-прогін: 250 запусків у кожному зразку

Для перевірки, чи короткі вибірки губили сигнал у вартості запуску процесу, повторено 30 перемішаних блоків із 250 запусків на зразок. RAPL читався від root через `sudo`; окремий тест показав приріст package-лічильника на 4,318 Дж за одну секунду. У звіті є 270 зразків, сирі відліки лічильників, температури й хеші виконуваних файлів.

| Виконуваний файл | Package RAPL, медіана Дж / 250 запусків | Парна різниця з idle, медіана Дж [p10, p90] |
|---|---:|---:|
| SENS native ELF | 36,14 | +1,29 [−4,32; +10,06] |
| C / GCC | 47,11 | −0,25 [−9,51; +10,45] |
| Rust | 23,94 | +1,06 [−1,77; +7,28] |
| Free Pascal | 38,95 | +1,59 [−5,56; +8,98] |
| C++ / Clang | 26,47 | +0,73 [−4,99; +8,70] |
| Zig | 18,08 | +0,38 [−5,45; +6,81] |
| Fortran / GFortran | 61,72 | +0,42 [−7,92; +16,32] |
| Swift | 72,07 | +4,22 [−5,98; +20,78] |
| Idle control | 19,98 | — |

Довший замір підтверджує, що сенсор збирає енергію за інтервалом, але фон і варіація package потужності лишають усі парні інтервали по обидва боки нуля. Тому й після збільшення вибірки не можна стверджувати, що одна мова витратила менше енергії. `perf stat` на цьому Linux також виводить `power/energy-pkg` як system-wide подію: це апаратний лічильник пакета, не per-process лічильник.

Дизасемблювання точних виміряних ELF підтверджує, що GCC C і Clang C++ замінили цикл арифметичною формулою, а Fortran зберіг цикл. Компілятори виконали різну кількість машинної роботи, попри спільний результат і близькі вихідні форми. Тому `N × запуски / час` — лише номінальна швидкість обсягу вихідної роботи, а не підтверджена кількість виконаних машинних ітерацій. Це один цикл на одному i5-6400, не рейтинг мов і не оцінка повної реалізації SENS.

Для нових джерел тип лічильника — беззнакове 32-бітне слово, індекс — 64-бітне беззнакове ціле, аргумент — десятковий текст командного рядка. Цикл працює з машинними цілими; динамічної пам’яті не виділяє. Повертається молодший байт суми як код завершення процесу. У Fortran проміжну суму нормалізовано за модулем 2³², щоб не покладатися на переповнення знакового цілого.

Питання для перевірки розуміння реалізацій:

1. Чому індекс має ширину 64 біти, а акумулятор — 32 біти?
2. Які відмінності в правилах переповнення між C++, Zig, Fortran і Swift тут нейтралізовані?
3. Які витрати benchmark враховує через окремий запуск процесу, а які не відображає через відсутність warm worker?

## Результат цього запуску

Початкові дані чотирьох варіантів залишені нижче як історичні. Вони були зібрані раніше і не є частиною двох розширених прогонів у таблиці вище.

| Виконуваний файл | Прогін 1: час / package RAPL | Прогін 2: час / package RAPL |
|---|---:|---:|
| SENS native ELF | 0,295 с (0,269–0,336) / 9,04 Дж (6,64–10,66) | 0,270 с (0,263–0,293) / 5,77 Дж (5,33–7,06) |
| C / GCC `-O2` | 0,397 с (0,367–0,436) / 12,11 Дж (8,89–13,31) | 0,365 с (0,357–0,394) / 7,64 Дж (6,90–10,45) |
| Rust `opt-level=2` | 0,184 с (0,163–0,228) / 5,86 Дж (4,30–7,66) | 0,162 с (0,153–0,177) / 3,81 Дж (3,26–5,03) |
| Free Pascal `-O2` | 0,308 с (0,288–0,339) / 9,52 Дж (7,24–10,63) | 0,289 с (0,279–0,300) / 6,29 Дж (5,68–8,53) |
| Idle-контроль: 50 запусків `/usr/bin/true` | 0,173 с (0,145–0,205) / 5,49 Дж (3,76–6,66) | 0,146 с (0,139–0,182) / 3,49 Дж (2,94–5,56) |

Числа в дужках — p10–p90 між 30 блоками. У другому прогоні вимірювач уже збережений у цьому каталозі й повністю перевірений; джерела workload і ELF ті самі. Загальне падіння RAPL в активних та idle-вибірках показує сильний вплив стану системи. Сирі дані обох прогонів збережені окремо; їх не об’єднано в один показник.

Це не рейтинг мов. GCC згортає суму в оптимізований цикл, Rust — у формулу з множенням, а SENS ELF та FPC виконують цикл. Отже, це порівняння цих бінарних файлів і їхніх компіляторних перетворень. Час включає старт процесу, завантаження ELF та (крім SENS) розбір десяткового аргументу.

Енергію за мовами визначити не вдалося. RAPL вимірює всю спільну апаратну зону, з фоновим навантаженням. Парна idle-діагностика після масштабування за тривалістю має інтервали, що охоплюють нуль; ці дані не дають пер-процесного споживання. Package/core/DRAM не додаються між собою.

SENS-бік тут — вузький генератор машинного циклу `BuildD12SumLoopELF` з фізичного D24 T5M, а не загальний source-to-native компілятор SENS. Це вимір поточної вузької нативної траси, не готовий бенчмарк повної мови чи REPL.

```bash
sudo -n env SUDO_USER="$USER" python3 -B evidence/energy-native-d12-loop-20261029/measure.py \
  --output "$PWD/evidence/energy-native-d12-loop-20261029/new-run.json"
```
