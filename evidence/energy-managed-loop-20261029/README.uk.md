# Окремі managed-runtime виміри циклу D12

Цей стенд зіставляє один і той самий цикл із `N = 8 388 361` у Go, Java HotSpot і .NET, а також перевіряє контрольний ELF, побудований наявним вузьким шляхом `BuildD12SumLoopELF` з фізичного T5M. Це профілі runtime й конкретного циклу, не рейтинг мов і не доказ повного компілятора SENS.

## Що запускається

- **Go 1.27.3:** AOT-бінарник і Go runtime, один процес та одна робоча нитка.
- **HotSpot 21:** tiered JIT увімкнений, SerialGC, heap 32 MiB, одна доступна JVM процесорна одиниця.
- **.NET 10:** Release IL, ReadyToRun вимкнений, tiered JIT/PGO, workstation GC, heap hard limit 32 MiB.
- **SENS контроль:** фізичний D24/T5M артефакт компілюється наявним FPC-шляхом і має завершитися кодом 173. Цей вузький шлях не є загальним SENS-компілятором.

Стенд фіксує дві різні умови. `cold` запускає кожний runtime як новий процес; кожен RAPL-відлік охоплює пакет із десяти незалежних cold-запусків (можна змінити `--cold-batch-reps`). `warm` виконує 50 циклів на запит у постійному процесі після окремого прогріву. Кожна відповідь містить кількість повторів, контрольну суму та лічильники GC. Сума перевіряється проти фізичного SENS ELF.

Для HotSpot зберігається підтвердження JIT-компіляції через `-XX:+PrintCompilation`; для .NET — дизасемблювання JIT через `DOTNET_JitDisasm`. Go позначений як AOT, без JIT. Збірка фіксує версії інструментів, командні прапорці, час компіляції, розмір і SHA256 артефактів.

## Запуск

```sh
bash evidence/energy-managed-loop-20261029/build.sh
python3 evidence/energy-managed-loop-20261029/test_measure.py
python3 evidence/energy-managed-loop-20261029/measure.py --check-only
sudo -E env DOTNET=/шлях/до/dotnet python3 evidence/energy-managed-loop-20261029/measure.py \
  --output evidence/energy-managed-loop-20261029/results.json \
  --rounds 30 --warmup 50 --batch-reps 50 --cold-batch-reps 10 --core 2
```

Повний режим записує окремі сирі RAPL-відліки у `.samples.jsonl` і звіт JSON. Порядок runtime рандомізовано в кожному парному блоці, CPU закріплено; GNU time вимірює RSS, а дочірній `RUSAGE_CHILDREN` — накопичений CPU час cold-процесів без округлення коротких запусків до сотих секунди. Також знімаються стійкий RSS, температури та завантаження хоста. Сирий package RAPL включає все споживання домену; парне масштабування idle — лише діагностична оцінка, а не енергія процесу. Хост має пройти 30 блоків кожної фази; стороннє навантаження може зробити результат непридатним.

## Межі висновків

Це один процесор i5-6400, один цілочисельний цикл, задані ліміти heap і параметри GC. Результат залежить від конкретних версій runtime/JIT, режиму прогріву та ОС. Warm-запити містять протокол stdin/stdout. RAPL не атрибутує енергію процесам, а idle-віднімання не перетворює його на процесний лічильник. Порівняння придатне для відтворюваних профілів цієї задачі; без довірчих інтервалів, відокремлених від нуля, не оголошувати переможця за енергією.
