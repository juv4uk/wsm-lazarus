# Швидка компіляція SENS на Free Pascal: інженерна стратегія

**Дата:** 30.10.2026  
**Статус:** дослідницька пропозиція та план перевірки, не ратифікація нового мовного закону, не доказ переваги FPC над Rust/SBCL і не готовий швидкий compiler mode.  
**Базовий зріз:** `wsm-lazarus/main@acd7913757446cbd7c09f4d85a96f451be7af52d`.  
**Задачі:** [#41](https://github.com/juv4uk/wsm-lazarus/issues/41) (нативна система класу SBCL), [#47](https://github.com/juv4uk/wsm-lazarus/issues/47) (компілятор/IR/backend); інтеграція з IDE — [#712](https://github.com/juv4uk/wsm-lazarus/issues/712).  
**Закон:** тільки pinned `external/sens@1f1bf676eeac605e065035d9dd2adaae807f1788`, Contract 12.0; `docs/native-system-roadmap.uk.md` залишається головною дорожньою картою.

## Теза

Free Pascal потенційно дасть швидкий цикл **збирання інструментів компілятора**, але це саме по собі **не доводить** швидкої компіляції програм SENS. Для низької затримки потрібен власний шлях **точний фізичний `.sens` (T5M) → допуск і зв'язування за Contract 12.0 → спільний WideIR → нативний код**, без повторного запуску FPC, асемблера чи компонувальника на кожен вираз у майбутньому REPL.

Архітектурний орієнтир SBCL — **клас компонентів** (інкрементальна компіляція, REPL, замикання, компілятор, оптимізатор, образи, налагоджувач), **не** Common Lisp semantics, не повторне втілення SBCL і не обіцянка рекорду.

### Чотири різні швидкості, які не можна плутати

| Показник | Початок → кінець | Що він доводить |
| --- | --- | --- |
| **Збирання самого компілятора** | сирці Pascal → бінарник компілятора FPC | швидкість циклу розробника компілятора; не швидкість компіляції SENS |
| **Холодна наскрізна AOT-компіляція SENS** | запуск компілятора + читання валідного T5M → готовий ELF | реальна затримка інструмента разом зі стартом процесу та I/O |
| **Гаряча компіляція у сеансі** | готові точні слова у вже запущеному compiler session → готові машинні інструкції | основна метрика інкрементального REPL; сьогодні це **ціль, не доведений загальний режим** |
| **Виконання та запуск результату** | ELF / образ → завершення задачі | швидкість машинного коду й cold start; не швидкість компіляції |

Не порівнювати FPC з Rust лише за словами «компілює швидше»: потрібні та сама робота, контроль бібліотек, залежностей, оптимізацій, розміру програми, середовища, I/O та вартості збирання.

## Цільова структура (пропозиція, не твердження про реалізацію)

```text
людський .lisp (укр)  → проєкція, НЕ семантичний оракул
                             │
                   точна структура і домени
                             │
канонічний T5M .sens ────────┘
                             ↓
       D2 рамка → domain/width/bits/law → callable admission
                             ↓
                    єдиний WideIR
                       /           \
                      /             \
         швидкий профіль          оптимізувальний профіль
       мінімальні доведені        додаткові доведені
       перетворення               оптимізації
               |                       |
               └────── нативний backend ──────┘
                             │
                код у пам'яті або ELF / образ
                             │
                спільний runtime + Lazarus IDE
```

**Швидкий профіль:** пропускати необов'язкові дорогі проходи; компілювати лише форми з доведеними ABI, callable admission і поведінкою. Не обходити перевірки ширини, закону, типів, арності, точного результату або безпеки виклику. Необізнана форма → явна відмова або перевірений fallback, **не** вигаданий opcode.

**Оптимізувальний профіль:** ті самі закони та WideIR, але вартісніші проходи (аналіз потоку, усунення перевірок лише за доказом, інлайнінг, спеціалізація D12+, замикання, хвостові виклики) вводити незалежними перевірюваними зрізами. `FPC -O1/-O2` налаштовує **збирання Pascal-компілятора**, а не автоматично оптимізацію SENS-програм.

**REPL-режим:** майбутня компіляція прямо в пам'ять потребує визначеного runtime ABI, життєвого циклу коду, відстеження коренів GC, прав доступу до виконуваної пам'яті та інвалідації коду при зміні визначень. Сам по собі готовий ELF або структурний SIR1 не доводить наявності такого REPL.

**Образи як у SBCL:** зберігати тільки перевірені частини runtime/оточення/скомпільованого коду, з контрольованими версією контракту, pin SHA, ABI і перевіркою сумісності. Не підмінювати швидкий запуск готового образу «часом компіляції» й не переносити хостові адреси як мовні тотожності.

## Що вже існує і чого ще немає

У `main` уже є вузькі фізичні маршрути `T5M → WideIR → ELF64`, дійсні машинні запуски та профільні перевірки збігу з pinned SENS; див. [дорожню карту](native-system-roadmap.uk.md) і [README](../README.md). Це не повний compiler для довільного `.sens`, не загальний runtime ABI, не доведений JIT, не закінчена система образів.

**Зона іншого агента — PR [#820](https://github.com/juv4uk/wsm-lazarus/pull/820):** затримка компіляції **16 канонічних програм** у трьох наявних AOT-механізмах (cold processes, одна пакетна компіляція, один постійний сеанс). Його методика має перевірки ідентичних ELF, їхнього виконання, сирі наносекунди й усі 6 перестановок порядку. **Не дублювати скрипти, workflow, fixtures, CLAIM або бенчмарк PR №820.** Цей документ визначає наступну архітектурну мету, а не повідомляє нові заміри.

Енерговимірювання компіляції окремі від RAPL-замірів **виконання** готового ELF; див. [чинний енергетичний стенд](energy-compiled-elf.uk.md). `energy=NOT_MEASURED`, доки немає відповідних апаратних даних.

## Правила доказовості швидкості

1. **Спочатку правильність:** відомий pin SENS/Contract 12.0, точна форма `.sens`, допустима ідентичність, негативні тести, stdout/exit-code parity з незалежним SENS REPL і фактичне виконання ELF.
2. **Потім час:** окремо зберігати `t_process_start`, `t_decode`, `t_admission`, `t_ir`, `t_opt`, `t_emit`, `t_link`, `t_machine_run` лише там, де справді є інструментовані часові межі; не виводити внутрішні етапи відніманням непорівнюваних запусків.
3. **Ті самі входи:** зміст програм, exact domain/width, CPU, OS, FPC/Rust версії, прапорці, pin, кодова база, робочий набір, прогрів, порядок запуску, час доби/навантаження фіксувати у свідку.
4. **Метрики:** сирі значення, медіана, p95, розкид, частка старту процесу, байти ELF, пікова пам'ять, кількість проходів; енергія окремо й тільки за реальним виміром. Пороги й «рекорди» не вигадувати.
5. **Чесне порівняння:** Rust reference, FPC SENS, SBCL і зовнішні системи можуть мати різні семантику та набір функцій. Порівняння компіляторів допускається лише для еквівалентної роботи; інше — позначити як **несумірні сценарії**.
6. **CI:** важкі бенчмарки — лише профільні/ручні, якщо так вирішено в #47; не додавати нічого до спільних push-workflow без узгодження. Профільний зелений CI не дорівнює загальній готовності SENS.

## Пропонований порядок наступних інженерних кроків

| Порядок | Найменший перевірюваний результат | Статус зараз |
| --- | --- | --- |
| 1 | Отримати висновок наявного PR №820 щодо трьох AOT-маршрутів із точним SHA й raw evidence | **Окремий активний PR; не дублювати** |
| 2 | Визначити стабільні межі вимірювання `T5M / bind / IR / emit` в одному підтриманому маршруті | **Пропозиція; не стверджувати готовим** |
| 3 | Один справжній **гарячий** компіляторний сеанс із кількома допустимими формами, стійким станом і independent oracle | **Потрібне окреме виконання і тести** |
| 4 | Два режими **того самого** WideIR з перевіркою побітової/семантичної рівності результатів | **Ціль; не реалізовано цим документом** |
| 5 | Скомпільована функція у REPL, спільна runtime ABI, GC, лексичні замикання та безпечне перевизначення | **Довгострокова ціль #41** |
| 6 | Порівняння з Rust і SBCL на узгоджених навантаженнях та незалежному залізі | **Тільки після доказів 1–5** |

**Критерій успіху:** відчутно менша затримка **перевірено коректної** компіляції SENS, а не швидший FPC сам по собі. Семантичний закон незмінний; швидкість не може купуватися прихованою підміною D1, D3, D12+, D2-рамки чи викличності.

## Межі цього коміту

Цей файл — **лише документація**: не змінює Pascal, Rust, Zig, `.sens`, таблиці доменів, CI, PR №820, існуючі тести або pinned джерело законів. Нових вимірювань і збірок тут немає. Усі майбутні claims слід підтверджувати окремим виконанням на exact SHA.
