# GЕ.8 — апаратна енергія чотирьох незалежних ELF64

Це **розширення вимірювання** уже перевіреного G6.64 (SENS native ELF64, GCC C,
Rust, Free Pascal), а не новий компілятор чи новий закон SENS.

## Входи та межі

- Єдиний мовний авторитет: pinned `juv4uk/sens@1f1bf676eeac605e065035d9dd2adaae807f1788`, Contract 12.0.
- Кожен із чотирьох випадків — canonical packed `.sens` D3:101 над двома D1,
  незалежно перевірений upstream SENS. `.lisp` — людська українська `укр`
  проєкція; D7 лише текст; числова площина починається із D12+.
- Порівняння охоплює **16 вже зібраних Linux x86-64 ELF**, кожен із повним
  SHA256 і фактичним точним побайтовим T5M-виходом. До вимірів повторно
  перевіряються всі 16 виконань і їхня відповідність маніфесту G6.64.
- Зіставляються **холодні запуски процесів**, разом із loader/startup, системними
  викликами stdout, накладними витратами на читання датчика та фоновим
  навантаженням. Це **не** чиста енергія однієї інструкції, не енергія
  компіляції, не різниця між алгоритмами й не доказ переваги мови.
- GCC, Rust, FPC можуть згортати сталі операнди ще при компіляції;
  SENS також може застосовувати лише ратифіковані оптимізації. Цей тест
  недостатній для узагальненого рейтингу. Суттєві навантаження,
  різні розміри даних, окремі компіляційні та warm режими потрібні надалі.

Історичний донор `juv4uk/mccarthy-eval` (x86-64 tagged cons,
`eval/apply/evcon/evlis`) корисний для архітектури, але **не** для підміни
семантики Contract 12.0 або для безпідставного перенесення його результатів
енергоефективності на SENS.

## Відтворення

На Linux x86-64 спочатку виконати наявний повний незалежний CI-профіль:

```bash
bash scripts/test-benchmark-elf-porivniannia.sh
python3 -B scripts/energy/test-compare-four-elf.py
python3 -B scripts/energy/compare-four-elf.py \
  --перевірка --корінь "$PWD" \
  --звіт "$PWD/build/m0.2/benchmark-elf-porivniannia/zvit/виміри.json" \
  --свідки "$PWD/build/m0.2/benchmark-elf-porivniannia/svidky"
```

У цьому режимі **16/16 ELF перевірені, але енергію НЕ виміряно**.

На контрольованій машині з доступним апаратним Linux powercap/RAPL
та уже зібраним `build/m0.2/bin/sensrapl` (див.
`scripts/energy/test-sensrapl.sh`) виконати:

```bash
python3 -B scripts/energy/compare-four-elf.py \
  --вимір --корінь "$PWD" \
  --звіт "$PWD/build/m0.2/benchmark-elf-porivniannia/zvit/виміри.json" \
  --свідки "$PWD/build/m0.2/benchmark-elf-porivniannia/svidky" \
  --rapl "$PWD/build/m0.2/bin/sensrapl" \
  --живлення /sys/devices/virtual/powercap/intel-rapl \
  --блоки 30 --повторів 30 --idle-ms 50 --макс-ват 1000 \
  --зерно 3468 --вихід "$PWD/build/m0.2/enerhiia-four-elf-real.json"
```

`--макс-ват` — **обґрунтована верхня межа** апаратної потужності зони,
а не виміряне значення: 1000 Вт тут лише приклад; оператор повинен
підставити перевірену межу обладнання. Вона потрібна для суворого допуску
випадків обертання RAPL. Кожен із 30+ переставлених блоків має 16
окремих вимірів і додаткову idle вибірку. Зберігаються сирі RAPL-DELTA1,
окремі `zones_uj`, абсолютний час і SHA256. **Не сумувати** вкладені
package/core/DRAM як незалежну енергію; **не віднімати** idle
автоматично. Несталі апаратні зони та неоднозначний wrap зупиняють
весь запис — без часткового JSON.

Без фізичного RAPL, дозволів або правильного результату інструмент
завершується з кодом 2, явним `ENERGY_NOT_MEASURED` та **не створює**
енергетичний звіт. GitHub Actions не створює жодних джоулів.

Протокол #346 зберігає CPU/governor/temperature та idle baseline як
необхідні метадані майбутньої контрольованої публікації; цей зріз
поки не встановлює температурного контролю, верифікації потужності,
профілів warm throughput чи статистичної значущості між мовами.
