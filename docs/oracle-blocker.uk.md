# Блокер: pinned SENS-оракул у цьому середовищі не збирається

**Дата:** 30.10.2026. **Пін:** `1f1bf676eeac605e065035d9dd2adaae807f1788`.

## Що це означає для статусів

`SENS_ORACLE_VERIFIED` для злитих verified-профілів лишається **NOT_VERIFIED**.
Це саме «не перевірено», а не «пройшло»: побайтова ідентичність старому
шляху доведена, а незалежна семантична звірка з REPL — ні.

## Де саме впирається (відтворювано)

1. `git clone https://github.com/juv4uk/sens` + `checkout <пін>` — **працює**,
   `rev-parse HEAD` збігається з піном.
2. Пінований **Zig 0.16.0** (потрібен `build.rs`) — завантажується й
   запускається, версія збігається з тією, що в `.github/actions/install-zig`.
3. `rustc 1.97.1` + `cargo 1.97.1` з Debian-пакетів у власний префікс —
   працюють; `hello.rs` збирається й виконується через саморобну `cc`-обгортку
   (`ld` + `crt1.o/crti.o/crtn.o`).
4. **Стіна:** `rustc --crate-name sens` падає з
   `memory allocation of 58720256 bytes failed` (SIGABRT) за будь-яких
   профілів: `release` з `lto=false`, `opt-level=1`, `codegen-units=16`,
   `jobs=1`, і `debug` — усі абортують на тому самому крейті.

Причина — ліміт пам'яті пісочниці: `/sys/fs/cgroup/memory.max` ≈ **2 ГБ**,
swap = 0. Це обмеження середовища, не проблема коду SENS.

## Як не витрачати на це півгодини

```sh
./scripts/check-oracle-feasibility.sh
```

Скрипт читає ліміт пам'яті й наявність `cargo`/`rustc`/`zig` та каже
вердикт за секунду. Коди виходу: `0` — середовище придатне для спроби,
`2` — заблоковано (пам'ять або немає cargo).

## Що робити тому, хто має більше пам'яті

Почати з кроку 4 на машині з ≥ 8 ГБ RAM: решта підготовки вже перевірена
й описана вище. Після успішної збірки — звірити фізичні результати
злитих verified-профілів з оракулом і лише тоді ставити
`SENS_ORACLE_VERIFIED`.

## Чого не робити

Не позначати `SENS_ORACLE_VERIFIED` на підставі побайтової ідентичності:
це перевіряє, що новий шлях робить те саме, що старий, а не що обидва
правильні щодо законів SENS.
