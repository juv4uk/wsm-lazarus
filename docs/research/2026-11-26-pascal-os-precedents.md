# Pascal як основа ОС: що з прецедентів справді перевірено

**Дата:** 26.11.2026
**Статус:** перевірка зовнішніх тверджень. **Не рішення** і не заклик: цей документ лише фіксує, що з поширеного переліку «ядер на Free Pascal» підтверджується першоджерелами, а що ні.
**Базовий зріз:** `wsm-lazarus/main`, Contract 12.0.

## Навіщо

Твердження «FPC придатний для ОС, бо є живі проєкти ядер» звучить переконливо рівно доти, доки не почнеш перевіряти список. Перевірка показала, що два найважливіші прецеденти **реальні й активні**, але описані в поширеному переказі неточно — і саме неточність робить аргумент слабшим, ніж він є насправді.

## Що підтверджено

### TORO — unikernel для microVM, а не монолітне SMP-ядро

TORO існує з 2003 року і зараз — це **unikernel для розгортання застосунків як microVM**. Архітектурно:

- ядро й застосунок працюють в одному кільці (ring 0), **без syscall** — лише виклики функцій;
- кооперативний планувальник, один планувальник на ядро, «одне ядро — одне завдання»;
- плоский образ пам'яті до 512 ГБ, без paging;
- `virtio-fs` і `virtio-vsocket` замість емуляції пристроїв;
- запускається під QEMU-KVM, Firecracker, Xen, VirtualBox.

Тобто TORO — це **живий доказ саме тієї моделі**, яку ми обговорюємо: довірене середовище, спільний адресний простір, відсутність ізоляції як свідомий вибір, а не як недогляд.

**Уточнення до поширеного переказу:** «монолітне ядро x86-64 з SMP і TCP/IP» — це TORO покоління 1.x (2003–2006) і проміжне покоління 2015 року. Сучасний TORO інший, і посилатися на нього як на доказ «моноліт із SMP» означає цитувати відгалуження, яке проєкт залишив.

### Ultibo — bare metal на Raspberry Pi, і не лише Pascal

Ultibo core — середовище розробки **без операційної системи** для Raspberry Pi (усі моделі, крім Pico). Активний: Core 2.6.173 від 09.02.2026, FPC 3.2.2, Lazarus 4.6U.

Що дає: витискальне багатопоточне планування, багатоядерність на Pi 2/3/4, повний стек IPv4 (TCP/UDP/ICMP/raw, DNS, DHCP), USB з драйверами Hub/Keyboard/Mouse/Storage/Network/HID, MMC/SD/SDIO, GPIO/I2C/SPI/PWM/UART/DMA, FAT12/16/32 + NTFS + CDFS, переривання й апаратні винятки, повний RTL.

**Уточнення:** Ultibo описує себе не як ОС, а як **unikernel або «ядро в RTL»**, і надає не лише Pascal, а й **C/C++ API**. Це важливо для нашої гібридної схеми: живий прецедент того, що ядро на Pascal і поверхня для C співіснують в одному образі, а не заважають одне одному.

## Чого я не підтвердив

У поширеному переліку також згадані FPOS (ядро з реалізацією Scheme для драйверів), FP-RTOS (real-time ядро для ARM), Asuro (x86 з NASM лише для bootstrap) і Jacqueline (ядро з графічним і звуковим стеком). Я **не знайшов** для них першоджерел у цій перевірці й не стверджую ні їхнього існування, ні їхнього стану. Якщо вони важливі для аргументу — потрібна окрема перевірка з посиланнями, а не згадка в списку.

Це не формальність: саме так у списках з'являються «мертві» проєкти, і саме тому наш власний README вимагає доказу й межі доказу для кожного рядка.

## Що з цього випливає для нас

1. **Модель «когерентність замість ізоляції» — не наша вигадка.** TORO реалізує її роками й свідомо: ring 0, без syscall, спільна пам'ять, кооперативне планування.
2. **Гібридний образ (Pascal + C + асемблер) — штатний режим**, а не компроміс: Ultibo постачає C/C++ API поверх Pascal-ядра.
3. **Швидкість ітерації — єдиний аргумент, який ми можемо виміряти самі.** Про нього є окремий протокол: [`chas-iteratsii.uk.md`](../chas-iteratsii.uk.md). Поки він не прогнаний, «FPC швидший за Rust на ранніх етапах» лишається гіпотезою, а не доказом.
4. **Немає підстав вважати, що FPC чогось принципово не вміє** для цієї мети: обидва підтверджені проєкти працюють на голому металі або під гіпервізором, з перериваннями, DMA, мережею й файловими системами.
