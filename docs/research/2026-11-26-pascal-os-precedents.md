# Pascal як основа ОС: що з прецедентів справді перевірено

**Дата:** 26.11.2026  
**Статус:** перевірка зовнішніх тверджень, не архітектурне рішення. Документ не змінює чинні ADR і не дозволяє Pascal у production-межі інших репозиторіїв.  
**Базовий зріз:** `wsm-lazarus/main`, SENS Contract 12.0.

## Навіщо

Теза «FPC придатний для ОС, бо є живі проєкти» потребує розділення різних типів систем: bare-metal runtime, unikernel, RTOS і повноцінна ОС — не взаємозамінні докази. Нижче залишено лише твердження, які можна прив'язати до першоджерела, і вказано межу кожного доказу.

## Що підтверджено

### FPOS — Pascal-ядро із Scheme-драйверами, проте незавершене

Офіційний README [rezgui/fpos](https://github.com/rezgui/fpos) описує мінімальне ядро на Free Pascal та Scheme-компоненти для ATA, PS/2, 8250 UART, FAT32 і RTC. README датує початок проєкту 2010 роком і прямо каже, що він потребує ревізії та нового завантажувача для 64-бітної архітектури.

У чек-листі *Implemented* позначені GDT/IDT, ISR (додатковий handler лише для page fault), IRQ, консоль, клавіатура, memory manager (із приміткою «needs testing»), speaker і RTC (із застереженням щодо часу). System calls, multitasking і filesystem залишені **непозначеними**. Далі README окремо попереджає, що частина файлів multitasking і filesystem не використовується через непридатний стан.

Це перевірений приклад експериментального FPC kernel із Scheme-драйверами та низькорівневими x86-компонентами; він **не** доводить готовність syscall ABI, багатозадачності чи файлової системи. Сам README каже «far from dead», але водночас вимагає ревізії — повторюємо саме це застереження, а не називаємо його зрілою ОС.

### TORO — два різні проєкти під однією назвою

В організації ToroKernel існують окремі репозиторії, які не можна зливати в один архітектурний опис:

**`torokernel/torokernel` — сучасний unikernel для microVM.** Його README описує:

- ціль x86-64 та до 512 ГБ RAM;
- запуск під QEMU-KVM microvm і Firecracker;
- кооперативний, орієнтований на I/O планувальник потоків;
- `virtio-vsock` для мережевої взаємодії та `virtio-fs` для файлової системи;
- вбудований GDB stub;
- застосунок і Toro працюють на одному рівні привілеїв, тому виклики до середовища — це звичайні виклики функцій, а не системні виклики;
- ціль — одна програма, потенційно багатопотокова.

README також має приклад між'ядерного обміну повідомленнями. Це свідчить про роботу з кількома ядрами у відповідному прикладі, але саме по собі не доводить наявність універсального SMP-планувальника. Тому не приписуємо сучасному Toro властивості, яких немає в його актуальному описі.

**Окремий `torokernel/ToroOS` — навчальна x86 ОС.** Її README прямо говорить про підтримку одного ядра. Перелічені POSIX, GRUB/Multiboot, багатозадачність, витискальне планування, VFS і FAT12; SMP, мережа, ext2 та IDE позначені як робота в процесі. Указано FPC 3.2.0 та `embedded-i386` RTL. Репозиторій не слід подавати як актуальне x86-64 SMP/TCP/IP ядро: це окремий, старіший навчальний проєкт.

**Висновок щодо поширеного твердження:** фраза «TORO — монолітне x86-64 ядро з SMP і TCP/IP» змішує різні репозиторії та перебільшує їхні поточні можливості. Сучасний `torokernel` — microVM unikernel; `ToroOS` — однопроцесорна навчальна ОС із мережевою підтримкою в планах.

### Ultibo — Pascal implementation із C/C++ поверхнею

Ultibo Core описує себе як embedded/bare-metal середовище без ОС, яке надає багато послуг, звичних для ОС: керування пам'яттю, мережу, файлові системи та threading. FAQ окремо називає його не операційною системою, а середовищем розробки для Raspberry Pi; також FAQ прямо каже, що Ultibo написаний повністю на Free Pascal і може працювати як unikernel або «kernel in a runtime library».

Водночас це не означає, що застосунки мусять бути написані лише Pascal: репозиторій Core документує окремий **C/C++ API** з потрібними заголовками та прикладами, стандартну C library, POSIX threads і стандартну C++ library. Коректне формулювання таке: **Core реалізований на Free Pascal, а платформа також надає C/C++ API та бібліотеки для прикладного коду.** Наявність C/C++ API не спростовує твердження про мову реалізації Core.

За офіційною сторінкою поточного стану Ultibo:
- Core 2.6.173 від 09.02.2026;
- FPC: Stable 3.2.2, Fixes 3.2.3, Main 3.3.1;
- Lazarus: Stable 4.6U, Fixes 4.7U, Main 4.99U;
- C/C++ API 1.0.129 від 26.01.2026.

README перелічує попереднє планування потоків, SMP на Raspberry Pi 2/3/4, IPv4 (TCP/UDP/ICMP/raw, DNS, DHCP), USB-пристрої, MMC/SD/SDIO, GPIO/I2C/SPI/PWM/UART/DMA, FAT12/16/32, NTFS, CDFS, переривання й апаратні винятки. Це сильний практичний прецедент для bare-metal embedded-платформи на FPC, але не доказ повноцінної десктопної ОС або готових x86-64 драйверів.

### KuroOS — історичний навчальний приклад x86

Окремо від початкового переліку знайдено [Kagamma/kuroos](https://github.com/Kagamma/kuroos), який описує себе як просту x86 ОС, написану на Free Pascal для навчання. README заявляє як наявні: PS/2 mouse/keyboard, VGA і VESA, ATA/ATAPI, read-only FAT32 та CDFS, PIC/RTC, preemptive multitasking, базовий window manager і userspace. У TODO залишено APIC, PCI, ACPI, ramdisk, запис у FAT32, ext2 та ELF loader.

GitHub API показує останній commit від 18.10.2021 (`dfcfdec`). Тому це корисний історичний доказ того, що FPC застосовували для x86 kernel із графічними й користувацькими компонентами, але не доказ сучасної підтримки, 64-бітності чи відтворюваної збірки: README-заяви не перевірялися нами запуском образу.

### Стан самого Free Pascal

Офіційна документація FPC усе ще називає 3.2.2 останнім stable-релізом. Розробка триває у гілці 3.3.x; щоденні development snapshots не мають гарантії стабільності чи офіційної підтримки. Сторінка Ultibo називає 3.3.1 поточною Main-версією у своїй матриці сумісності. Отже, для відтворюваних експериментів потрібно фіксувати точну версію компілятора й RTL, а не писати просто «FPC latest».

## Чого я не підтвердив

FPOS має перевірене першоджерело й описаний окремо вище. Для FP-RTOS, Asuro і Jacqueline у цьому проході не знайдено достатньо надійних першоджерел, щоб підтвердити саме ці проєкти, їхній код, цільові архітектури та стан реалізації. Я не роблю висновку, що їх не існує; лише не використовую ці назви як доказ без окремого аудиту.

## Що з цього випливає для наших репозиторіїв

1. FPC доведено застосовувався для bare-metal embedded-систем і unikernel-моделей. Це підтверджує технічну придатність інструмента для окремих класів систем, але не визначає архітектуру наших проєктів.
2. Ultibo показує, що FPC-реалізація може співіснувати з C/C++ прикладним API. Це корисний приклад інтероперабельності; він не є аргументом автоматично переносити C або Pascal у будь-яку production-межу.
3. Toro корисний як архітектурний приклад вузького unikernel для microVM, але не як підтвердження властивостей повноцінної SMP/TCP/IP ОС.
4. Швидкість компіляції FPC та енергія на ітерацію залишаються гіпотезою до власного заміру. Протокол для цього — [`chas-iteratsii.uk.md`](../chas-iteratsii.uk.md); не переводити непоміряні секунди в заявлену стратегічну перевагу.
5. **Межа `wsm-os-lisp` незмінна:** ADR-004 визначає production target як Pure Lisp + мінімальний x86-64 ASM. Це дослідження FPC не скасовує ADR-004. У `wsm-lazarus` FPC може бути окремим субстратом/свідком для експериментів і перевірки відповідності SENS; його роль визначається відповідним ADR цього репозиторію.
6. Перед будь-якою зміною архітектури потрібне окреме рішення власника з доказами, міграційним планом і перевіркою всіх залежних ADR/ABI/CI, а не висновок із переліку зовнішніх проєктів.
