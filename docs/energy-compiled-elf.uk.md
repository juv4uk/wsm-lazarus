# GЕ.5 — реальна енергія виконання скомпільованого SENS ELF64

## Що вимірюється

Єдиним мовним авторитетом є pinned `juv4uk/sens@1f1bf676eeac605e065035d9dd2adaae807f1788` (Contract 12.0). Канонічний вхід і вихід — фізичні паковані `.sens` (T5M). `.lisp` у `укр` — людська проєкція, а не оракул. D7 визначає ратифіковане текстове відображення, D12+ — окрема числова площина; жодного перетворення з текстових імен у викличні закони немає.

Для чотирьох справді підтриманих форм **D3:101(D1:0|1,D1:0|1)** наявний `sensmashyna --тотожність` компілює фізичний T5M через перевірений ExactIR у справжній Linux x86-64 ELF64. `test-sensmashyna.pas` лише генерує фізичні свідки; незалежний pinned SENS REPL підтверджує D1-відповідь до будь-якого заміру. Згенерований ELF реально запускається, а його **байтовий T5M stdout** порівнюється з очікуваним фізичним свідком. Наявний `sensvykon` виконує **ту саму** форму, з незалежно перевіреною D1 відповіддю, але його текстовий stdout — не канонічні машинні байти.

Усі порівняння — **cold process**: готовий ELF запускається знову без компіляції, FPC evaluator запускається з нуля з фізичним admission. Це порівняння **двох end-to-end шляхів виконання однієї вузької форми**, а не чистих машинних інструкцій чи різних мов за однаковим алгоритмом. Нативний backend не переписує Core1/Core4.

## Команди

CI/локальна передперевірка (потрібні FPC 3.2.x, Linux x86-64, pinned upstream Rust/Zig CLI, `git`, Python 3):

```sh
bash scripts/energy/test-compiled-elf.sh
```

Справжній RAPL-вимір: після складання тих самих п'яти бінарників і генерації фізичних свідків (як у `test-compiled-elf.sh`) запустіть, указавши реальні шляхи:

```sh
python3 scripts/energy/compiled-elf.py \
  --корінь "$PWD" --свідки "$PWD/build/energy/свідки" \
  --машина "$PWD/build/energy/bin/sensmashyna" \
  --виконавець "$PWD/build/energy/bin/sensvykon" \
  --читач "$PWD/build/energy/bin/senst5m" \
  --оракул "$PWD/sens-oracle/target/release/sens" \
  --rapl "$PWD/build/energy/bin/sensrapl" \
  --живлення /sys/devices/virtual/powercap/intel-rapl \
  --вимір --блоки 30 --повторів 500 --макс-ват 1000 \
  --вихід "$PWD/build/energy/compiled-elf-real.json"
```

`--макс-ват` — **консервативна фізична верхня межа потужності зон**, потрібна існуючому `sensrapl` для виключення неоднозначного wrap. Вона не є результатом вимірювання. Значення 1000 Вт — приклад, який треба перевірити на вимірюваному апаратному забезпеченні. Однакові за розміром блоки й переставлений порядок допомагають виявити дрейф; тривалість idle вимірюється окремо і не автоматично віднімається з результатів.

У режимі `--вимір` потрібні справжні доступні powercap RAPL-зони та новий шлях для результату. Програма зберігає **всі сирі зональні мкДж, час у мкс, кількість виконань, SHA256 джерела/ELF/очікуваних відповідей, порядок і номер блоку** лише після повного успіху. Вкладені RAPL-зони ніколи не підсумовуються; зміна списку зон, зіпсовані числа, пропущені датчики, переповнення або багаторазовий wrap призводять до відмови.

## Чесні межі доказу

* GitHub Actions **не має гарантованого доступу до фізичних RAPL**; виконує реальні FPC/ELF/SENS-перевірки та негативи синтетичного протоколу, але **не створює показники джоулів**.
* RAPL вимірює споживання **апаратної зони**, включно з іншими процесами, стартом процесу, зовнішнім читанням датчика і фоновим навантаженням. Це не енергія конкретного процесу; idle не можна механічно відняти як його споживання.
* Для порівняння C, Rust та Free Pascal потрібні **окремі семантично зіставні програми**, однакові точність, робота, довжина блоку, компіляційні прапорці та обладнання. Цей зріз не надає рейтингу мов, швидкості однієї інструкції чи загальної підтримки SENS.
* Для коротких блоків похибка й фон можуть переважати корисний сигнал; збільшуйте `--повторів` і контролюйте температуру, governor, фонове завантаження та порядок.
* `scripts/energy/test-compiled-elf.sh` ідентифікує відсутні RAPL як **ENERGY_NOT_MEASURED**, а не як **0 Дж**. Помилковий byte-exact свідок повністю відхиляється.

Питання для інженерного перегляду: (1) Чому compiled ELF порівнюємо лише після oracle parity? (2) Чому RAPL zone ≠ process joules? (3) Чому idle не віднімаємо автоматично? (4) Чому D1 stdout і packed D1 T5M різні фізичні подання? (5) Чому компіляція не входить у вимір готового ELF?
